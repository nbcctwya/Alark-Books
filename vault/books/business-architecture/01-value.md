# 找到付费的理由

「我会做什么」和「别人为什么愿意付费」之间，往往隔着一段需要认真观察的距离。能力可以列成清单，付费的理由却总是发生在具体场景中。

这本书以一家虚构的内容工作室为例。它最初提供剪辑、文案与海报设计，后来发现小型企业真正反复提出的问题，是怎样把零散的产品资料变成一份能够被销售团队使用的内容包。

## 把需求写成一个场景

我们把服务对象收束为准备发布新产品的小团队。对方需要在两周内完成一份介绍材料、三个演示片段与一套常见问题说明。工作室能够提供的承诺因此有了范围，也有了可以核对的结果。

| 要问的问题 | 样例中的回答 |
| --- | --- |
| 谁在使用成果 | 产品与销售团队 |
| 何时需要完成 | 新产品介绍会之前 |
| 要解决什么阻碍 | 资料分散，难以统一表达 |
| 如何确认交付 | 内容包通过约定的检查清单 |

## 从模糊意愿到明确约定

需求讨论需要把「想要高级一点」这样的表达，转成可以检查的具体事项。例如画面要包含哪些场景，文案要回答哪些问题，哪些材料必须由客户提供。讨论越清楚，后续协作越容易定位分歧。

> [!note] 工作记录 01
> 为一个真实服务写下对象、场景、成果和边界。先让对方确认这四件事，再讨论具体形式。

这一步的结果不是一句漂亮的定位口号，而是一份能够指导接下来工作的简短说明。下一章将把它接到[[02-delivery|交付流程]]上。
